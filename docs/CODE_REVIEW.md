# Код‑ревью проекта Rutube Cinema Hub
Дата: 2026-02-08

## Цель документа
Оценить текущее состояние проекта, зафиксировать проблемы, варианты решений и способы усиления уже принятых удачных решений, чтобы приблизить проект к лучшим мировым практикам.

## Краткий обзор архитектуры
- **Frontend**: React 18 + TypeScript + Tailwind CSS.
- **Backend**: Express (`server.js`) с прокси `/api/proxy` и эндпоинтами KinoRate AI.
- **Интеграции**: Rutube API/скрапинг, LLM провайдеры (Gemini/Mistral).
- **Сборка**: Vite (dev/prod).

## Сильные стороны и как их усилить
1) **Гибридное проксирование Rutube (fallback на публичные прокси).**
   - Усиление: добавить метрики отказов/латентности по каждому прокси и авто‑черный список на период (circuit breaker).
   - Усиление: конфигурировать список прокси через env/конфиг, а не в коде.

2) **Богатая UI‑логика и UX‑детали (скелетоны, модалки, fallback‑изображения).**
   - Усиление: добавить систематические e2e сценарии (Playwright/Cypress) для главных пользовательских потоков.
   - Усиление: документировать UX‑паттерны в отдельном `docs/UX_GUIDE` (без раздувания кода).

3) **Наличие сервисного слоя (`services/*`) и типизации (`types.ts`).**
   - Усиление: разделить доменные типы по контекстам (rutube, kinorate, ui) и добавить barrel‑файл.
   - Усиление: внедрить Zod/Valibot для runtime‑валидации ответов API.

## Текущие проблемы и рекомендуемые решения
1) **Крупный монолитный компонент `App.tsx`.**
   - Риск: сложная поддержка, высокая связанность и низкая тестируемость.
   - Решение: выделить в модули `useRutubeData`, `useVideoCache`, `useFilters`, `useHistory`, UI‑секции (Header, Grid, Modals) и вынести бизнес‑логику в hooks/services.
   - Дополнительно: провести ревизию state‑менеджмента и подумать о Zustand/Redux Toolkit для сложного состояния.

2) **Отсутствие изолированной структуры `src/`.**
   - Риск: «шум» в корне, усложнение масштабирования.
   - Решение: перенести код в `src/`, настроить пути в tsconfig/vite (alias), оставить в корне только конфиги и docs.

3) **Ограниченные тесты.**
   - Риск: регрессии, особенно в парсинге и прокси‑логике.
   - Решение: добавить unit‑тесты на `rutubeService` (парсинг, fallback), интеграционные тесты на `/api/proxy`, и UI‑тесты на критические сценарии.

4) **Отсутствие строгой валидации внешних данных.**
   - Риск: падения при изменениях Rutube/LLM форматов.
   - Решение: добавить схемы данных (Zod/Valibot), отбрасывать невалидные результаты, логировать несоответствия.

5) **Логирование без корреляции запросов.**
   - Риск: трудно анализировать цепочку событий.
   - Решение: добавить requestId/traceId и прокидывать через фронт и бэк (headers), логировать с единым контекстом.

6) **Смешение concerns в `server.js`.**
   - Риск: трудно расширять и тестировать backend.
   - Решение: разбить на папки: `server/routes`, `server/services`, `server/middleware`, `server/config`; вынести proxy и LLM в отдельные модули.

7) **Недостаточная обработка rate limits для внешних API.**
   - Риск: блокировки и деградация.
   - Решение: throttling и backoff, кеширование результатов KinoRate и Rutube, ограничение параллелизма.

8) **Отсутствие формализованной документации архитектуры.**
   - Риск: сложнее onboarding и масштабирование.
   - Решение: добавить `docs/ARCHITECTURE` и `docs/STATE_MANAGEMENT` согласно правилам в `PROJECT_RULES.md`.

9) **Безопасность прокси.**
   - Риск: SSRF, утечки.
   - Решение: строго ограничить домены, добавить allowlist для `rutube.ru`, логирование подозрительных URL, rate limit на `/api/proxy`.

10) **Недостаточная детализация ошибок в UI.**
    - Риск: пользователь не понимает, что происходит.
    - Решение: централизовать обработку ошибок и показывать читабельные сообщения; добавить status‑модуль.

## Лучшие практики, к которым стоит стремиться
- Clean architecture: четкое разделение UI, домена и инфраструктуры.
- Observability: структурированные логи + метрики + трассировка (OpenTelemetry).
- Автоматизация качества: linting (ESLint), форматирование (Prettier), проверка типов (tsc), pre‑commit hooks.
- CI/CD: пайплайн для линтинга, тестов, сборки, smoke‑test.
- Документация: ADR (Architecture Decision Records) и changelog.

## Рекомендованный план улучшений (итеративно)
1) Разделить `App.tsx` и сервер на модули.
2) Добавить тесты вокруг `rutubeService` и proxy.
3) Внедрить валидацию данных и улучшить логирование.
4) Упорядочить структуру проекта (`src/` + алиасы).
5) Автоматизировать качество (ESLint/Prettier/CI).

## Контрольные критерии успеха
- `App.tsx` < 500 строк, логика вынесена в hooks/services.
- Есть unit + integration тесты на критические ветки.
- Внешние данные валидируются и ошибки отображаются пользователю.
- Корень проекта чист, документация актуальна.
